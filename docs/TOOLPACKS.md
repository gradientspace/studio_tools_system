# Tool Pack Contract (API version 1)

A **tool pack** is a folder, usually its own git repo, that provides one or more tools. The Studio Tools server syncs the packs listed in `toolpacks.json`, serves them to Studio along with the framework, and hot-reloads them like everything else.

Start a new pack with `npm run new-pack -- <dir> [packId]`. It creates the manifest, an example tool, the generated `SDK.luau` and an `AGENTS.md`/`CLAUDE.md` for agents working in the pack, and registers the pack in `toolpacks.local.json`. Options: `--name "Pack Name"`, `--tab Tab`, and `--empty` (no example tool). `toolpacks/core` in this repo is the fuller reference pack.

## Adding a pack

Packs are listed in two files at the root of the studio_tools_system repo, with the same format:
- `toolpacks.json` (committed): packs everyone gets, such as `core`.
- `toolpacks.local.json` (gitignored): your own packs. `npm run new-pack` adds new packs here. Paths in it are specific to your machine, so they never end up in the repo.

Folders in `user_toolpacks/` (gitignored) that contain a `toolpack.json` are loaded without being listed anywhere, and new ones are picked up while the server runs. The Tools Agent chat puts the tools it creates in `user_toolpacks/user/`.

```json
{
  "packs": [
    { "path": "toolpacks/core" },
    { "git": "https://github.com/someone/their_tools.git", "ref": "main" },
    { "path": "../my_tools_in_progress" },
    { "git": "https://github.com/someone/old_pack.git", "enabled": false }
  ]
}
```

- `path`: a local folder, relative to the file it's listed in. Edits are hot-reloaded. Use this while developing a pack.
- `git`: cloned (shallow) into `.toolpacks/` the first time the server sees it. `ref` is a branch or tag (defaults to the remote's default branch). Run `npm run sync-packs` to pull the latest; a running server hot-reloads the result. The cache is managed by the server, so don't edit files there.
- `enabled: false` skips an entry without removing it.

Saving either file while the server is running takes effect immediately.

## Pack layout

```
toolpack.json          manifest (required, at the pack root)
src/                   Luau source; the folder named by "source"
  SDK.luau             generated by `npm run export-sdk`; commit it (see The SDK)
  Tools/               every ModuleScript directly in here is a tool
    MyTool.luau
    BigTool/           a folder with init.luau is one tool with helper modules
      init.luau
      Helpers.luau
  Shared/              anything else: base classes, helpers, data (any names)
```

Only `.lua`/`.luau` files are served. Each file becomes a ModuleScript (Rojo conventions: `init.luau` turns its folder into a ModuleScript). Hidden files and `node_modules` are skipped.

In Studio, the pack's source folder appears as `StudioTools.Packs.<packId>`, so modules in a pack can require each other with normal relative paths (`script.Parent.Parent.Shared.Blocks`).

### toolpack.json

```json
{
  "id": "core",
  "name": "Core Tools",
  "version": "0.1.0",
  "apiVersion": 1,
  "tab": "Core",
  "description": "Basic block tools.",
  "source": "src"
}
```

| Field | Required | Meaning |
| --- | --- | --- |
| `id` | yes | Unique across all packs; letters, digits, `_`, `-`. Stable: saved tool settings are keyed on it. |
| `apiVersion` | yes | The Studio Tools API version the pack targets (see Versioning). |
| `tab` | no | Palette tab the pack's tools appear in (default `"Core"`, at most 24 characters). Packs naming the same tab share it; tabs appear in the order of the first pack that names them in the config. A tool can override it with its own `tab` (see Tabs and sections). |
| `name` | no | Shown as a heading when a tab holds tools from several packs (defaults to `id`). |
| `version` | no | The pack's own version, shown next to its heading in shared tabs. Semver recommended. |
| `description` | no | Free text. |
| `source` | no | Folder containing the Luau source, relative to the pack root (default `.`). |

## The SDK

Pack code reaches the framework only through the SDK. Each pack carries a generated `SDK.luau` at the root of its source folder, and modules require it with a normal relative path:

```lua
-- from Tools/MyTool.luau or Shared/Something.luau
local SDK = require(script.Parent.Parent.SDK)
```

`SDK.luau` contains the full type definitions for the SDK and `ToolContext`; it's the in-repo reference for the API. At runtime it just returns the framework's real SDK. Generate or refresh it from the studio_tools_system repo:

```sh
npm run export-sdk -- path/to/pack     # or no argument: every local pack in toolpacks.json
```

Commit `SDK.luau` in the pack's repo. `npm run check` warns when it's missing or out of date. (Requiring `script:FindFirstAncestor("StudioTools").SDK` directly also works, but type checking can't follow it.)

| Member | |
| --- | --- |
| `SDK.API_VERSION`, `SDK.MIN_API_VERSION` | API versions this build of the framework supports |
| `SDK.isApiVersionSupported(n)` | |
| `SDK.Tool` | Base class for all tools |
| `SDK.InputBehavior` | Base class for input behaviors (see Input) |
| `SDK.SingleClickInputBehavior`, `SDK.ClickDragInputBehavior`, `SDK.ClickOrDragInputBehavior`, `SDK.HoverInputBehavior` | The standard input behaviors |
| `SDK.CaptureState` | Values returned by input behavior methods |
| `SDK.Maid`, `SDK.Signal` | Cleanup and event utilities |
| `SDK.Terrain` | Higher-level terrain edits: height fields, raise/lower/flatten/smooth/paint/fill over polygons and paths (see Terrain) |
| `SDK.ToolContext`, `SDK.ToolDefinition`, `SDK.SettingSchema`, ... | Exported types (`SDK/Types.luau`) |

Anything under `StudioTools.System` is internal; don't require it from a pack.

### Libraries

Shared Luau libraries listed in studio_tools_system's `libraries.json` (e.g. `geometry3luau`) are installed with the plugin and mounted at `StudioTools/Libraries/<name>`:

```lua
local G3 = require(script:FindFirstAncestor("StudioTools").Libraries.geometry3luau)
local DMesh3 = require(script:FindFirstAncestor("StudioTools").Libraries.geometry3luau.DMesh3)
```

`npm run check` resolves these requires, so a misspelled module is an error. A library's source is in `.libraries/<name>-<tag>/src/` of the studio_tools_system repo after `npm run sync-libraries` (or a check). Requiring a library's individual modules directly, as with `DMesh3` above, keeps their types; fields of a package table that loads modules lazily are untyped. Libraries are part of the installed plugin, not the hot-reloaded build, so a pack that needs a library (or a newer version of one) needs the user to update `libraries.json`, reinstall the plugin and restart Studio.

## Tools

A tool module returns a **class** derived from `SDK.Tool`:

```lua
local SDK = require(script.Parent.Parent.SDK)

local MyTool = SDK.Tool:extend({
	apiVersion = 1,                 -- required
	id = "MyTool",                  -- required; unique within the pack
	name = "My Tool",               -- required; palette label
	version = "1.0.0",              -- optional; the tool's own version
	description = "What it does.",  -- optional
	order = 10,                     -- optional; sort order within the pack
	tab = "Model",                  -- optional; palette tab (default: the pack's tab)
	section = "Blocks",             -- optional; section within the tab (default: the pack's name)
	settings = { ... },             -- optional; see Settings
})

function MyTool:activate(ctx: SDK.ToolContext)
	-- required
end

function MyTool:deactivate(ctx: SDK.ToolContext, reason: SDK.ShutdownReason)
	-- optional; reason is "Done", "Accept", "Cancel" or "Force"
end

function MyTool:onAction(key: string)
	-- optional; a "button" setting was clicked (see Settings)
end

function MyTool:canActivate(): (boolean, string?)
	-- optional; called on the class: can the tool start now? (see below)
	return true
end

return MyTool
```

When the user picks the tool, the framework creates a fresh **instance**, `setmetatable({ ctx = ctx }, MyTool)`, and calls `instance:activate(ctx)`. Store per-activation state on `self`; read class fields (`self.id`, `self.settings`, ...) through it. When the tool is deactivated, `instance:deactivate(ctx)` runs, then everything created or connected through `ctx` is cleaned up automatically.

Its full id is `<packId>/<toolId>`, e.g. `core/PlaceBlock`.

**Tabs and sections.** The palette shows one tab per tab name and lays out each tab's tools in sections. A tool's tab is its `tab` field, or else its pack's `tab`; its section is its `section` field, or else its pack's `name`. So by default each pack's tools form one section in the pack's tab, and setting `tab` / `section` lets one pack spread its tools over several tabs, or several packs share a section. Tabs and sections appear in order of first appearance: packs in config order, tools in `order` within each pack. A tab with more than one section shows a label above each.

**Starting conditions.** A tool that only makes sense in some situations, e.g. with a MeshPart selected, overrides `canActivate()`. It's called on the class (`self` is the tool class; there is no `ctx` yet) whenever the palette shows the tool and again after every selection change. Returning `false, "reason"` greys out the tool's button and adds the reason to its tooltip; the system won't start the tool then. It must be quick and must not yield (a yielding or erroring `canActivate` counts as available). The tool should still check in `activate()` what it needs.

```lua
function Sculpt:canActivate(): (boolean, string?)
	local selected = game:GetService("Selection"):Get()
	if #selected == 1 and selected[1]:IsA("MeshPart") then
		return true
	end
	return false, "Select a MeshPart to sculpt."
end
```

A tool is rejected, with a warning in Studio's Output window, if:
- the module doesn't return a class derived from `SDK.Tool`;
- `apiVersion` is missing or not supported;
- `id` or `name` is missing, or `id` is a duplicate within the pack;
- `tab` or `section` is set but isn't a non-empty string (or `tab` is over 24 characters);
- `activate` isn't overridden.

### Shutdown overlay

While a tool is active, the system shows buttons at the bottom-center of the viewport for exiting it. Tools never create these themselves. A tool picks the style with a `shutdown` field:

```lua
local MyTool = SDK.Tool:extend({
	...
	-- Default: one "Done" button.
	shutdown = { type = SDK.ShutdownType.Done, done = { text = "Finish", tooltip = "Stop placing blocks" } },
})

local OtherTool = SDK.Tool:extend({
	...
	-- Two buttons: Accept (green) and Cancel (red).
	shutdown = {
		type = SDK.ShutdownType.AcceptCancel,
		accept = { text = "Apply", tooltip = "Keep the new layout" },
		cancel = { tooltip = "Put everything back" },   -- text defaults to "Cancel"
	},
})
```

Every `text` and `tooltip` is optional. The defaults are the button's name and "Exit <tool name> (Esc)" / "Keep the changes and exit <tool name>" / "Discard the changes and exit <tool name> (Esc)". Escape triggers Done, or Cancel for Accept/Cancel tools; it's ignored while a text box has focus. The system reads the options by calling `self:getShutdownOptions()` right after `activate()`. The default implementation returns the `shutdown` field (or Done); override it when the options depend on state.

`deactivate(ctx, reason)` receives one of `SDK.ShutdownReason`:

| Reason | When |
| --- | --- |
| `Done` | the user clicked Done, or pressed Escape (Done-style tools) |
| `Accept` / `Cancel` | the user clicked Accept / Cancel, or pressed Escape (Cancel) |
| `Force` | anything else: the user picked another tool or clicked the active tool's palette button, Studio switched to one of its own tools, the plugin is unloading, or `activate()` failed |

#### Refusing a shutdown, and disabling Accept

Clicking a shutdown button or pressing Escape is a *request*. Before the tool shuts down, the system calls:

```lua
-- May yield. Return false to keep the tool running. trigger is "Button" or "Escape".
function MyTool:confirmShutdown(reason: SDK.ShutdownReason, trigger: SDK.ShutdownTrigger): boolean
	if reason == SDK.ShutdownReason.Cancel and self.hasUnsavedWork then
		return self.ctx:confirm({
			title = "Discard changes?",
			message = "Your edits will be lost.",
			confirmText = "Discard",
			cancelText = "Keep Editing",
		})
	end
	return true
end
```

`ctx:confirm(options)` shows a modal dialog in the viewport and yields until the user answers. While it's open, viewport clicks don't reach the tool, and Escape answers "no". It also returns false if the tool is shut down meanwhile. `ctx:alert({ title?, message, buttonText? })` is the one-button version, for telling the user something (e.g. why Accept failed); it yields until dismissed. While a `confirmShutdown` call is running, the shutdown buttons are greyed out. A `confirmShutdown` that does slow work on Accept (an upload, building meshes) should also show `ctx:showProgress({ title?, message })`: a modal dialog with an animated bar that blocks viewport input and Escape until `handle:close()` (or deactivate). Update its text with `handle:setMessage(text)`; close it before showing an `alert`. The core pack's Save As MeshPart tool does this. If `confirmShutdown` errors, the shutdown goes ahead, so a bug can't trap the user in a tool. `Force` shutdowns don't call it and can't be refused.

For Accept/Cancel tools, the system also polls `canAccept()` (about 10 times a second, and right before accepting) to enable or disable the Accept button:

```lua
function MyTool:canAccept(): (boolean, string?)
	if not self.hasSelection then
		return false, "Select something first"   -- shown as the disabled button's tooltip
	end
	return true
end
```

Call `ctx:refreshShutdownButtons()` after a state change to update the button immediately instead of on the next poll. The core pack's Paint tool uses all of this.

What each reason means is up to the tool. For Accept/Cancel, a convenient pattern is to open one undo recording in `activate` (`self.session = ctx:beginUndo("My Tool")`), then call `self.session.commit()` on Accept and `self.session.cancel()` on Cancel. Cancelling the recording reverts everything done during it. For `Force`, choose a sensible default; keeping the changes matches how Studio's own tools behave.

Clicks on the overlay buttons never reach the tool's input behaviors, so clicking Done never also acts on the scene behind it.

### Input

Tools don't listen to the mouse. They add **input behaviors**, and the system's InputManager routes mouse input to them. It guarantees that:
- only the active tool's behaviors get input;
- only one behavior captures the mouse at a time;
- a capture is ended if the tool shuts down, the behavior is removed, or Studio loses focus.

Add behaviors in `activate()`:

```lua
function MyTool:activate(ctx: SDK.ToolContext)
	self:addInputBehavior(SDK.ClickDragInputBehavior:new({
		hitTest = function(point: SDK.InputPoint): number?
			local part, hit = ctx:partAt(point)
			return if part and hit then hit.Distance else nil   -- nil: not a target
		end,
		onBeginDrag = function(point, modifiers) ... end,
		onUpdateDrag = function(point, modifiers) ... end,
		onEndDrag = function(point, modifiers) ... end,
	}))
end
```

Callbacks get an `SDK.InputPoint`, `{ position: Vector2, ray: Ray }`: the viewport position and the world ray through it. `ctx:raycastAt(point)` and `ctx:partAt(point)` cast that ray. They also get `SDK.Modifiers`, `{ shift, ctrl, alt, cmd }` booleans. A tool can add several behaviors, and add or remove them while it runs (`self:addInputBehavior`, `self:removeInputBehavior`).

#### Standard behaviors

All of them take a `hitTest(point)` that returns the distance along `point.ray` to something the behavior should act on, or nil. Callbacks can be passed as options or assigned to the behavior later. `id` and `priority` are optional. `button` (`"Left"` by default, `"Middle"` or `"Right"`) picks the mouse button for clicks and drags. Middle- and right-button input is currently disabled in the InputManager, because Studio pans and rotates the camera on those drags, so `"Middle"` and `"Right"` behaviors never start.

| Behavior | Callbacks | Behavior |
| --- | --- | --- |
| `SDK.SingleClickInputBehavior` | `onClick` | Press and release on a target. `hitTest` runs again on release, and the click only fires if it still hits, so moving off the target cancels. |
| `SDK.ClickDragInputBehavior` | `onBeginDrag`, `onUpdateDrag`, `onEndDrag`, `onCancelDrag` | A press on a target starts the drag at the press point. Every input update while the button is held calls `onUpdateDrag`, including modifier keys going up or down, camera moves, and the release itself. The release then calls `onEndDrag`. If the drag is taken away, `onCancelDrag()` runs, or `onEndDrag` at the last point if there's no `onCancelDrag`. |
| `SDK.ClickOrDragInputBehavior` | `onClick`, plus the drag callbacks | A click if the release is within `dragThreshold` pixels (default 4) of the press. Otherwise a drag that begins at the press point once the mouse moves further. |
| `SDK.HoverInputBehavior` | `onBeginHover` (defaults to `onUpdateHover`), `onUpdateHover`, `onEndHover` | Hover only: active while `hitTest` hits and no other behavior has a better hover. |

#### How input is routed

The system turns every mouse event, modifier key change, camera move, undo/redo and setting edit into an `SDK.InputState`. It holds:
- `point` and `previousPoint`;
- a `ButtonState` (`pressed`, `down`, `released`) for each of `left`, `middle`, `right`, `shift`, `ctrl`, `alt` and `cmd`;
- `time`.

`pressed` and `released` are true only in the update where the change happened.

- **Capture.** While nothing is capturing, every behavior is asked `wantsCapture(input)`. All of them are always asked, because any one might have the nearest hit.
  - A behavior answers nil, or `{ depth = number }`.
  - Requests are ordered by `priority` (lower first, default 100), then by depth (nearest first). `beginCapture` is tried on each in turn until one returns `"Begin"`; `"Ignore"` passes to the next.
  - The capturing behavior then gets every update through `updateCapture` until it returns `"End"`, followed by `endCapture`.
  - `forceEndCapture` replaces `endCapture` when the capture is taken away.
- **Hover.** Behaviors with `enableHover = true` are asked `wantsHover(input)` on every update that isn't captured, and the best request hovers.
  - The hovering behavior gets `beginHover`, then `updateHover` while it stays the best, then `endHover`.
  - Hover is paused, not ended, while something captures, and resumes on the update that ends the capture.
- While the mouse is over system UI in the viewport (the shutdown buttons, the chat box), or a dialog is open, nothing starts capturing and hover ends.
- **Methods must not yield.** Use `task.spawn` for slow work. A method that yields, or errors, counts as failed: it doesn't capture or hover, or its capture is force-ended. It's reported once in the output.

For something the standard behaviors don't cover, extend `SDK.InputBehavior` and override its methods:

```lua
local MyBehavior = SDK.InputBehavior:extend({ id = "MyBehavior", enableHover = true })

function MyBehavior:wantsCapture(input: SDK.InputState): SDK.CaptureRequest?
	if input.left.pressed and input.alt.down then
		return { depth = 0 }
	end
	return nil
end

function MyBehavior:beginCapture(input: SDK.InputState): SDK.CaptureState
	return "Begin"
end
-- updateCapture, endCapture, forceEndCapture, wantsHover, beginHover, ...

local behavior = MyBehavior:new({ someOption = 1 })   -- fields copied onto the instance, then init()
```

A tool that keeps its own list of behaviors can override `getInputBehaviors()` and call `ctx:inputBehaviorsChanged()` when the result changes. `ctx:refreshInput()` re-runs input at the current mouse position after the tool changes something its hit tests depend on. Undo/redo, setting edits and camera moves already do this.

Behaviors are the only way tools get mouse input; the context has no mouse events and no `PluginMouse`. For keyboard shortcuts, use `ctx:onKey` and `ctx:isKeyDown`.

### Inheritance

Any tool class can be extended. Base classes normally live outside `Tools/`, e.g. in `Shared/`:

```lua
-- Shared/PartPickerTool.luau
local PartPickerTool = SDK.Tool:extend({ apiVersion = 1 })

function PartPickerTool:onPick(part)
	error("must implement onPick")      -- "pure virtual"
end

function PartPickerTool:activate(ctx)
	...                                 -- shared behavior: adds input behaviors that call self:onPick(...)
end

-- Tools/Erase.luau
local Erase = PartPickerTool:extend({ apiVersion = 1, id = "Erase", name = "Erase" })

function Erase:onPick(part)
	...
end

function Erase:activate(ctx)
	PartPickerTool.activate(self, ctx)  -- calling the base version is explicit
	...
end
```

A base class that has to live in `Tools/` (for example, so other packs can find it) can set `abstract = true`; it's then skipped when listing tools. `abstract` is read with `rawget`, so subclasses don't inherit it.

`SDK.Tool` deliberately doesn't define `apiVersion`, so every tool states the API version it was written against, either directly or through a base class in its own pack. Declaring it on each tool is recommended.

### Settings

`settings` is an array of schemas, and the palette builds the tool's settings panel from it, in order. Tools never create settings widgets themselves. Values are saved across Studio sessions and are available as `ctx.settings[key]`. `ctx:onSettingChanged(fn(key, value))` fires on edits. A tool can change its own settings with `ctx:setSetting(key, value)` (e.g. from a keyboard shortcut): the value is coerced and saved like an edit, the palette shows it, and `onSettingChanged` handlers run.

| `type` | Extra fields | Widget | Value |
| --- | --- | --- | --- |
| `"number"` | `min`, `max`, `step` | text field, or a slider (`extended.widget`) | number, snapped to `step` and clamped to `min`/`max` |
| `"integer"` | `min`, `max`, `step` (whole, default 1) | text field, or a slider (`extended.widget`) | whole number |
| `"string"` | `maxLength` | text field | string |
| `"boolean"` | | On/Off toggle | boolean |
| `"color"` | `presets` (array of Color3) | swatch that opens a color picker (saturation/brightness square, hue bar, hex field, the presets) | Color3 |
| `"enum"` | `options` (array of strings) | dropdown | one of `options` |
| `"button"` | | full-width button | none: an action (see below) |
| `"label"` | | full-width text (its `label`) | none: display only |

Every schema has `key` and `type`, optionally `label`, `tooltip` and `extended`, and every type except `"button"` and `"label"` has a `default`. A `tooltip` shows when the mouse rests on the setting's row for half a second. A `"label"` row shows its `label` as wrapped text; change the text with `ctx:setSettingState(key, { label = ... })`. A `"number"`, `"integer"` or `"string"` setting with `readOnly = true` shows its value in a field the user can't edit (never a slider), for values the tool reports, such as a triangle count; the tool sets it with `ctx:setSetting`, and it isn't remembered between sessions.

**Extended options.** `extended` is a table of presentation options; they change how a setting is shown, never its value, and options that don't apply to the type are ignored:

| Option | Types | Meaning |
| --- | --- | --- |
| `widget = "field"` / `"slider"` | number, integer | A text field (default) or a slider with the value in a small field beside it. A slider needs `min` and `max`; without them it falls back to a field, with a warning. |
| `placeholder = "..."` | string | Grey hint text while the field is empty. |

```lua
settings = {
	{ key = "radius", label = "Radius", type = "number", default = 8, min = 1, max = 64, step = 0.5, extended = { widget = "slider" } },
	{ key = "count", label = "Count", type = "integer", default = 5, min = 1, max = 50, tooltip = "How many to place" },
	{ key = "name", label = "Name", type = "string", default = "", maxLength = 40, extended = { placeholder = "Model name" } },
	{ key = "info", label = "Select parts, then press Generate.", type = "label" },
}
```

Sliders and the color picker change the value continuously while dragging, so `ctx:onSettingChanged` fires for each step.

**Actions.** A `"button"` setting is drawn as a full-width button labeled `label`. Clicking it calls the tool's `onAction(key)` method, in its own thread, so it may yield:

```lua
local MyTool = SDK.Tool:extend({
	...
	settings = {
		{ key = "segments", label = "Segments", type = "number", default = 9, min = 3, max = 40, step = 1 },
		{ key = "generate", label = "Generate", type = "button", tooltip = "Build it from the selection" },
	},
})

function MyTool:onAction(key: string)
	if key == "generate" then
		self.ctx:setSettingState("generate", { enabled = false, label = "Working..." })
		...
	end
end
```

**Widget state.** `ctx:setSettingState(key, { visible?, enabled?, label?, tooltip? })` shows or hides a setting's row, enables or disables it (a disabled widget is greyed out and can't be edited or clicked), replaces its label (a button's text) or its tooltip (`""` removes it). It works for every type. Only the fields given change, and every widget starts visible, enabled, and with its schema's label and tooltip each time the tool activates.

**Status line.** `ctx:setStatus(text)` shows a line of text under the tool's name in the palette, e.g. progress or the result of an action; `ctx:setStatus(nil)` hides it.

Status and widget-state changes update the palette in place, so they don't interrupt a value the user is typing.

### Viewport panels

Put a tool's controls in its settings panel: values as settings, actions as `"button"` settings, and progress in the status line. When a tool needs UI in the viewport itself, it asks the system for a panel instead of creating its own ScreenGui:

```lua
local panel = ctx:createViewportPanel({ position = "Top" }) -- or "TopLeft", "TopRight"
local label = Instance.new("TextLabel")
label.Text = "Hello"
label.TextColor3 = SDK.ViewportStyle.text
label.Parent = panel
```

- `createViewportPanel` returns a Frame styled like the system's viewport UI (the Tools Agent chat): dark background, rounded corners, padding, sized to its contents, with a horizontal `UIListLayout` named `Layout`. Fill it with your own GUI objects. You may restyle it, e.g. change its colors or set `panel.Layout.FillDirection` to Vertical.
- `SDK.ViewportStyle` has the colors, fonts and sizes of that style (`panel`, `field`, `button`, `accent`, `text`, `dimText`, `errorText`, `font`, `boldFont`, `textSize`, `cornerRadius`, `padding`, `rowHeight`), for styling the panel's contents to match.
- Clicks inside a panel don't reach the tool's input behaviors, so clicking a button on it won't also pick the part behind it. Keep the panel's contents inside its bounds: only the panel's own area is protected.
- Panels at the same position stack downward. They're removed when the tool deactivates.

### ToolContext

The `ctx` passed to tools. Its type is `SDK.ToolContext`; the README has the full table. Briefly:
- **State:** `ctx.settings`, `ctx.state`, `ctx.toolId`.
- **Input:** `inputBehaviorsChanged`, `refreshInput` (see Input); keyboard: `isKeyDown`, `isShiftDown`, `onKey`.
- **Picking:** `raycastAt`, `partAt`, at an input point.
- **Previews:** `createBoxPreview`, `createHighlight`, `createAdornment`, `createTemporaryModel` (see Temporary scene content).
- **Undo:** `recordUndo`, `beginUndo`, `onUndoRedo`; `addUndoStep` for the tool's own state (see Undo for tool state).
- **Tool UI:** `setStatus`, `setSettingState` (see Settings), `createViewportPanel` (see Viewport panels).
- **Camera:** `focusView(cframe, size)` animates the camera to frame a box (its center and orientation, and its size), keeping the current view direction and making the box center the camera's orbit point. `centerView(point)` pans (no rotation or zoom) so a world point is at the center of the view, and makes it the orbit point. Tools bind these to keys themselves, e.g. F with `ctx:onKey`. (While no tool is active and the palette is open, the system itself binds C to center the view on the surface under the mouse.) `autoCameraSpeed(size)` sets Studio's camera fly speed (WASD) and mouse-wheel zoom step to suit an object of that size, so small and huge objects are both comfortable to move around. Those speeds are user preferences shared by all places, so the values from when the tool started are restored when it deactivates (and, if Studio closed first, the next time the plugin starts).
- **Tools Agent:** `askAgent` (see below).
- **Meshes:** `saveLocalMesh`, `clearLocalMesh` (see Local meshes), `uploadMesh` (upload a MeshPart's mesh as a new Mesh asset; yields, errors with a message for the user).
- **Cleanup:** `connect`, `addCleanup`.

### Temporary scene content

For previews, `ctx:createAdornment(className)` makes any `HandleAdornment` (`"LineHandleAdornment"`, `"SphereHandleAdornment"`, `"ConeHandleAdornment"`, ...) adorning the Terrain, so its `CFrame` is world space; like `createBoxPreview` it lives in CoreGui. (`CylinderHandleAdornment` rings with an `InnerRadius` don't render; draw rings from line segments.)

For real 3D content, such as a preview mesh, `ctx:createTemporaryModel(name?)` returns a `Model` in the Workspace. It and everything put in it are made non-archivable, so they're never saved with the place, copied, or recorded in undo history (Studio's undo ignores non-archivable instances), and parts in it are locked and ignored by `ctx:raycastAt`. It's destroyed when the tool deactivates. To hide a part of the place while a preview stands in for it, set its `LocalTransparencyModifier`, which is local to Studio and not saved or recorded; restore it in a cleanup.

### Undo for tool state

Studio's undo history only covers the place. A tool that edits state of its own, such as a mesh it keeps in memory, records each edit with `ctx:addUndoStep(name, undo, redo)` after making it. That adds a Studio waypoint named `name`, so Ctrl+Z, Ctrl+Y and the undo buttons undo and redo the tool's edits in order with everything else; `undo()` and `redo()` run while the tool is active and must not yield. Adding a step drops any steps that were undone. After the tool deactivates its waypoints stay in Studio's history but do nothing when undone.

Internally each step sets an attribute (`StudioToolsUndoStep`) on the Workspace, since a waypoint needs a change Studio tracks; the attribute is removed on deactivate.

### Local meshes

A MeshPart made from an EditableMesh (`AssetService:CreateMeshPartAsync(Content.fromObject(editable))`, or `ApplyMesh` from such a part) loses its mesh when the place is saved and opened again: Studio doesn't save EditableMesh content. A tool that leaves such a part in the place calls `ctx:saveLocalMesh(part)` after creating or changing it, inside the same undo recording. The system gives the part a mesh id (attribute `StudioToolsLocalMeshId`, tag `StudioToolsLocalMesh`), stores the mesh on the dev server in the background, and gives it back whenever the place is opened (see "Local meshes" in the README). Call it again after editing the same EditableMesh to update the stored copy. A tool that gives such a part a regular mesh asset calls `ctx:clearLocalMesh(part)`. The core pack's Bake Transform, Sculpt and Save As MeshPart tools show how.

### Tools Agent requests

`ctx:askAgent(prompt, options?)` sends a prompt to the Tools Agent, the coding agent behind the chat box. The agent can edit the open place through the Roblox Studio MCP, so a tool can hand it work, e.g. "make the clicked part look like a stone wall". The call never yields. It returns an `SDK.AgentRequest`, and the result arrives later:

```lua
function MyTool:deactivate(ctx: SDK.ToolContext, reason: SDK.ShutdownReason)
	if reason ~= SDK.ShutdownReason.Accept or not self.part then
		return
	end
	local request = ctx:askAgent(`Add a sign to the front of {self.part:GetFullName()} that says "Shop".`)
	request:onFinished(function(result: SDK.AgentResult)
		if result.ok then
			print("Agent:", result.reply)
		else
			warn("Agent request", result.status, result.error)
		end
	end)
end
```

- **Waiting.** `request:await()` yields until the request finishes and returns the `SDK.AgentResult`: `ok`, `status` (`"done"`, `"failed"` or `"cancelled"`), `reply` (the agent's final text reply) and `error`. Input behavior callbacks must not yield, so call `await` from `task.spawn`, or use `request:onFinished(fn)`. Requests usually take tens of seconds or more.
- **Progress.** `request.status` is `"sending"`, `"queued"` (`request.position` is its place in the queue), `"running"`, then one of the final statuses. `request.result` is set once it's finished.
- **Queueing.** Requests run in the chat's agent session, one at a time, after whatever the agent is already doing. Each shows up in the chat as a message labeled with the tool's name, and the agent's replies appear there too. The chat's Stop button stops the current request and cancels the queued ones. At most 10 can be queued.
- **Cancelling.** `request:cancel()` finishes it as `"cancelled"` right away. A queued request is dropped; a running one stops the agent, and changes it already made to the place stay.
- **Lifetime.** A request outlives the tool that sent it, so a tool can send one when it's accepted. Pass `{ cancelOnDeactivate = true }` to cancel it when the tool deactivates instead. Requests also survive hot reloads, but not a restart of the dev server: they then fail.
- **Prompts.** The agent is told that the prompt comes from a tool, that it should act on the place through MCP rather than edit code, and that its final reply goes back to the tool. Include what it needs to find things, such as `instance:GetFullName()`. If the tool needs to parse the reply, ask for an exact format ("Reply with only the new part's full name").
- **Failures.** A request fails with an `error` when the agent isn't available, the server can't be reached, or the agent hits an error. Changes the agent makes through MCP aren't part of the tool's undo recordings.

## Terrain

`SDK.Terrain` is a library of higher-level edits of the place's smooth terrain, for tools that shape terrain procedurally from user input (a drawn polygon, a clicked path, a brush stroke). It works on **voxel columns** (4 × 4 studs) and their **surface height**, the top of the topmost solid terrain in the column. Every option is documented in the `Terrain*` types in `SDK.luau`.

```lua
local Terrain = SDK.Terrain

ctx:recordUndo("Raise Hill", function()
	-- a hill over the polygon, peaking in its middle, capped into a mesa
	Terrain.raiseWithinPolygon(points, { height = 60, maxHeight = 20, falloff = "smooth" })
	-- a river: carve along the path, then fill with water up to the banks
	Terrain.lowerAlongPath(riverPoints, { height = 10, radius = 6, falloffWidth = 12, widthScale = { 0.5, 2 } })
	Terrain.fillAlongPath(riverPoints, { radius = 12, level = 0 })
end)
```

The edits don't record undo (call them inside `ctx:recordUndo` / `ctx:beginUndo`) and don't yield unless `yield = true` is passed, so a small edit can run from an input behavior callback; a brush-sized edit takes a few milliseconds. Each returns `{ columns, region, heights?, snapshot? }`: how many columns changed, the voxel region written, with `returnHeights` (or `dryRun`, which computes without writing, e.g. for a preview) the new surface heights, and with `snapshot = true` a copy of the voxels it changed: `Terrain.restore(snapshot)` puts them back, so a tool can redo an edit with new settings (the core pack's terrain curve tools do this).

**Shapes.** `Terrain.polygon(points)` is an area; `Terrain.path(points, { closed?, radius?, widthScale?, heightScale? })` is a stroke along a polyline (one point makes a dot, i.e. a round brush). Points are `Vector3`s, or `Vector2`s as (X, Z); a path made of `Vector3`s has a height along it, which `flatten` and `fill` use by default and the other edits use with `base = "path"`. Every shape edit takes either kind (`Terrain.raise(shape, options)`), and there are shortcuts that take the points (`raiseWithinPolygon`, `raiseAlongPath`, ...; path options go in the same table). `widthScale` and `heightScale` vary a path along its length: one value per point is interpolated along each segment; any other count is spread evenly by arc length, so two values go from start to end. `Terrain.circle` and `Terrain.smoothPath` (Chaikin corner rounding) help make points.

**Falloff.** A shape covers each column by its distance to the shape: the ramp is `falloffWidth` studs wide and runs inward from a polygon's edge (`falloffAlign = "inside"`; the default width then reaches the middle of the polygon), or outward from a path's radius (`"outside"`), or across the edge (`"center"`). `falloff` shapes the ramp: `"linear"`, `"square"`, `"sqrt"`, `"smoothstep"`, `"round"`, `"constant"`, a function, or `"smooth"`, which also blurs the distance field (`smoothing`, in studs, can be set for any falloff) so the ridges and peak of a polygon's distance field and sharp corners are rounded.

| Edit | What it does |
| --- | --- |
| `combineWithHeightField(field, options)` | Interpolates a grid of heights (`{ min, max, values[i][j], weights? }`, cubic or linear) at each column and combines it with the surface by `mode`: `replace`, `max`, `min`, `stamp` (adds `value * multiplier`), `blend` / `blendMin` (smooth max / min within `blendRadius`). `edgeFalloff` fades it out toward the field's edges. |
| `raise` / `lower` | Raises (lowers) by `height` × the falloff weight (× the path's `heightScale`), at most `maxHeight` (a flat top). `mode = "stamp"` (default) follows the terrain; the other modes combine `base ± that` with it, with `base` a height, `"path"`, or measured around the shape (`"boundaryMin"`, `"boundaryMean"`, `"boundaryMax"`). |
| `flatten` | Moves the surface to `level` (default: the path's height, else the mean height around the shape), blending out over the falloff. |
| `smooth` | Blurs the surface heights (`radius`), weighted by the falloff. |
| `paint` | Sets the material of the solid voxels within `depth` of the surface; can scatter the edge (`dither`), and be limited to `onlyMaterials` and to a slope range (`minSlope`, `maxSlope`, degrees). |
| `fill` | Fills the air above the surface up to `level` (default: the path's height, else the lowest point around the shape, so a basin fills to its rim) with `material`: Water (the default) goes in the liquid channel, so it fills around partial voxels; Air drains water. |
| `modifyHeights(min, max, fn)` | Moves each column's surface to `fn(x, z, height)`, for any height function. |
| `modifyVoxels(region, fn)` | Calls `fn(position, material, solid, liquid)` for every voxel and writes what it returns. |
| `surfaceHeight(x, z)`, `readHeightField(min, max)`, `sampleHeightField(field, x, z)` | Reading surface heights, e.g. for previews or to edit them and write them back with `combineWithHeightField`. |

How heights are written:
- **Raising** fills from just below the old surface up to the new one, with `material` or else the surface's own material, so caves below stay.
- **Lowering** pushes the top of the terrain down instead of cutting it. The terrain from the surface down to `pushDepth` (8) moves down rigidly, and the band of `compressionDepth` (16, at least 1.25× the drop) below it is squeezed, so a thin layer (a bridge, a ledge) sinks instead of being cut through. On solid ground it's the same as cutting. `pushDepth = 0, compressionDepth = 0` cuts instead.
- **Empty columns.** A column with no terrain counts as having its surface at `emptyHeight` (0), so raising there builds terrain up from that height.
- **Searching.** Surfaces are searched for between `searchMinY` (-1024) and `searchMaxY` (2048).

Terrain heights follow the mesher's rule (measured in Studio, and what `Terrain:FillBlock` writes): a column whose topmost solid voxel is centered at `c` with occupancy `o`, over full voxels, has its surface at `c + 4o`.

## Rules for pack code

- **No side effects at require time.** Every module in a build is required up front to validate it. Do work in `activate`, not at the top level of a module.
- **Clean up through `ctx`.** Instances, connections and undo recordings registered with `ctx` are released on deactivate. Anything else, you must clean up in `deactivate`.
- **Make undoable changes inside `ctx:recordUndo` / `ctx:beginUndo`.** Studio allows only one open recording at a time, so a `beginUndo` while another recording is open (e.g. a session-long one) does nothing, and its changes join the open recording.
- **Resync after undo/redo.** The user can undo or redo while a tool is active, which changes the place without the tool knowing. If a tool keeps state about the place (counts, cached parts, previews), refresh it in `ctx:onUndoRedo(fn(action, waypointName))`. Prefer state you can recompute from the place itself, like Paint's "differs from the original" count, over counters that undo can't update.
- **A broken pack is dropped, not fatal.** If any module in a pack fails to compile or load, that pack's tools are omitted from the build (errors go to the Output window and the palette marks the pack as failed). Other packs and the framework reload normally.

## Checking and debugging

These run from the studio_tools_system repo and are designed to work without anyone watching Studio.

**`npm run check`** checks the framework, the loader and every pack in `toolpacks.json` without needing Studio. It exits non-zero on errors.
- **Pack manifests and layout:** problems are errors. A missing or outdated `SDK.luau` is a warning.
- **Luau code:** syntax, types and lints, checked with [luau-lsp](https://github.com/JohnnyMorganz/luau-lsp) against Roblox's plugin API and the same instance tree the loader builds. That means `script.Parent...` requires and `ctx:` calls are checked, provided parameters are annotated (`ctx: SDK.ToolContext`).
  - Syntax and type errors fail the check; lints are warnings.
  - Files are checked in Luau's default lenient mode; add `--!strict` at the top of a file for stricter checking.
  - luau-lsp is downloaded into `.tools/` on first run.

**`logs/studio-tools.log`** collects the server's events and the Studio output that mentions `StudioTools`, which includes:
- builds being served and loaded;
- pack and tool load failures (including the engine's syntax error messages);
- tool validation warnings;
- runtime errors and stack traces from any module in the tree.

The plugin forwards that output to the server, which also echoes it in its terminal. The file is cleared when the server starts.

Suggested loop for changing a pack (with `npm start` running and Studio open):
1. Edit the pack.
2. `npm run check` and fix anything it reports.
3. Save. The server picks up the change and Studio hot-reloads it (unless a tool is active; the reload waits for it).
4. Read the end of `logs/studio-tools.log`. A `Loaded build N` line means the reload happened; a pack or tool failure lists the errors with module paths like `StudioTools.Packs.<packId>.Tools.MyTool:42`.

Static checks can't verify everything the framework checks at load time, such as a tool class's `apiVersion` or a missing `activate` override. Those show up as warnings in the log after a reload.

## Versioning

`apiVersion` is a single integer covering everything in this document: the manifest, the folder layout, the tool class contract, `ToolContext`, and the SDK.

- **Additive changes** (new `ctx` methods, new optional fields, new setting types) don't change the version.
- **Breaking changes** (removing or changing behavior, renaming, changing signatures) bump `SDK.API_VERSION`.
- The framework loads packs and tools whose `apiVersion` is between `SDK.MIN_API_VERSION` and `SDK.API_VERSION`. Older versions can be kept working with compatibility shims keyed on the tool's `apiVersion`. Anything outside that range is skipped with a warning naming the supported versions.
- A pack's `version` and a tool's `version` are the author's own and are informational only.
